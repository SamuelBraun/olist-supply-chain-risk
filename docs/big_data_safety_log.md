# Big-data-safety log

Every intentional departure from big-data-safe PySpark in this project is listed here, per the CLAUDE.md §3 hard rule and the assignment brief's instruction to "indicate anywhere explicitly that you have not used big data safe functionality, and why." The registry constants in `src/olist/safety.py` are the IDs referenced by `# BIG-DATA-SAFETY-ESCAPE: <ID>` comments in the codebase. `src/olist/checks.py` enforces that every ID in code is catalogued here (and vice versa).

The dataset is ~100k orders / ~100k reviews — all escapes below would break at 10–1000× scale. The "production alternative" column names what we would use if Olist's data grew to marketplace-peer size.

| ID | Call site(s) | What it does | Why it's a safety escape | Production-scale alternative | Why acceptable at this size |
|---|---|---|---|---|---|
| `TOP50_VIZ` | `pipeline.convergence.top50_for_quadrant()` | `risk.orderBy("risk_score" DESC).limit(50).toPandas()` — the 50 highest-risk sellers for the quadrant scatter. | `toPandas` materialises all 50 rows on the driver. | Write the top-50 aggregate to parquet, render the chart in a BI tool (Tableau / Metabase) sourced from that parquet. | 50 rows × ~8 columns ≈ 4 KB — trivial on the driver. Capped by an explicit `limit(50)` after `orderBy`, so the cost is bounded even at unlimited input scale. |
| `STATE_AGG_VIZ` | `pipeline.convergence.state_mean_risk()` | `groupBy(seller_state).agg(mean).toPandas()` for the state bar chart. | `toPandas` materialises the groupBy result on the driver. | Same: write aggregate to parquet, render in BI tool. | Brazil has 27 states → 27 rows × 3 columns. Aggregation happens in Spark; only the reduced result is pulled. |
| `RISK_NORM_AGG` | `pipeline.convergence.normalise_score()` | `df.agg(F.min, F.max).first()` to extract min/max scalars for min-max normalisation, then broadcast the scalars back as literals. | `.first()` is a driver-side `collect()` on a one-row aggregate. | Spark-native: compute min/max via a broadcast join of the aggregate back to the DF. Or use `ml.feature.MinMaxScaler` inside a Pipeline (requires the input column to already be a `Vector`, which would need an extra `VectorAssembler` round-trip). | The aggregate is literally one row; the scalar-then-`F.lit` pattern is idiomatic Spark for normalisation constants and is cheaper than a self-join. |
| `LSTM_TO_PANDAS` | `pipeline.sentiment.train_lstm()` | `text_labelled.toPandas()` on the pre-filtered DataFrame that feeds the PyTorch LSTM. | Pulls 43,337 rows × 2 cols (text + label) into the driver as pandas. | `spark-nlp` (John Snow Labs) for distributed transformer-style training, or Petastorm for streaming Spark partitions into a distributed PyTorch job via Horovod / Ray Train. | 43k rows × short Portuguese strings ≈ 15 MB; fits comfortably in the 6 GB driver memory configured in `spark_session.py`. The LSTM is the MANDATORY deep-learning rubric item per the brief; at this size, going distributed would be over-engineering. |
| `LSTM_PYTORCH` | `pipeline.sentiment.train_lstm()` | The LSTM model itself (PyTorch `nn.LSTM` + DataLoader training loop). | PyTorch is not a Spark primitive; training runs on the driver CPU. | `spark-nlp` ships production-grade text classifiers that distribute via Spark workers; for custom nets, Petastorm → PyTorch DDP. | The rubric explicitly asks for a Deep Learning demonstration, and the brief's FAQ confirms the dataset is small by design. PyTorch on CPU trains the masked-mean-pool LSTM in ≤5 min and produces AUC=0.9630 (see `decisions_log.md` 2026-04-22 NB2 entry). |
| `TOP10_PAGERANK_DRIVER` | `pipeline.network.compute_bfs_backups()` | `seller_pagerank.orderBy(desc).limit(10).collect()` to produce the driver-side list of seed seller IDs for the BFS backup loop. | `.collect()` pulls a DataFrame into the driver as Python objects. | Use `GraphFrames.bfs` with a `fromExpr` that selects the top-10 directly in the GraphFrame query (possible in theory; in practice the GraphFrames BFS API requires a scalar `fromExpr` per call). Alternative: `motif` to express all "top-10-to-other-seller" paths in one graph query. | 10 rows of seller IDs (UUID strings ≈ 400 bytes). The BFS itself then runs distributed on the JVM. |
| `BFS_BACKUP_COLLECT` | `pipeline.network.compute_bfs_backups()` | Inside the per-seller BFS loop: `paths.limit(1).collect()` to extract the first alternative seller along a reachable path. | Each iteration materialises at most one row on the driver. | Same as above — the BFS result set would ideally be produced graph-wide in a single call, not per-seed. | `limit(1)` caps each call at one row; the loop runs 10 times max (the TOP10_PAGERANK_DRIVER cap). |
| `LEAD_INDICATOR_VIZ` | `pipeline.sentiment.lead_indicator_cross_corr()` | `lag_df.toPandas()` on the 9-row lag-vs-correlation summary for the inline chart. | Driver-side materialisation. | Write to parquet, render chart in BI tool. | 9 rows × 3 cols by construction — correlation is computed per lag inside Spark via `F.corr(...).first()`; only the summary is pulled. |
| `PANDAS_MATPLOTLIB_VIZ` | `viz.py` (all helpers); every `plt.*` call in `00_main.ipynb` and the three thematic notebooks. | pandas DataFrames + matplotlib / seaborn for static chart rendering. | pandas and matplotlib are single-node libraries. | Write the aggregate to parquet; render in a BI tool (Metabase, Tableau, Superset) sourced from the parquet. For notebooks specifically: `plotly` with server-side rendering, `pyspark.pandas` for pandas-API-on-Spark plotting. | Every chart in this codebase is driven from a pre-aggregated / pre-capped Spark frame (`TOP50_VIZ`, `STATE_AGG_VIZ`, `LEAD_INDICATOR_VIZ`). pandas never sees raw data. |
| `SMALL_SUMMARY_COLLECT` | Row-count audits and sanity-check `.first()` / `.collect()` calls on one-row aggregates (e.g. `row_counts.first()`, dropped-row diffs). | Driver-side scalar extraction from an aggregated DataFrame. | Log the aggregate to a metrics sink (Prometheus, a metadata table) rather than emitting a Python `print(...)`. | The aggregate is always one row; this is the idiomatic Spark pattern for "reduce to a scalar for a log line". |

## How to add a new escape

1. Add a constant to `src/olist/safety.py` with a short docstring describing the call site.
2. Add a row to this table with the same ID.
3. In the offending source code, tag the line with `# BIG-DATA-SAFETY-ESCAPE: <ID>`.
4. `src/olist/checks.py::check_safety_log_consistency()` passes iff the three surfaces agree.
