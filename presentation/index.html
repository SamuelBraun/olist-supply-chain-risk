Why this is a big-data challenge

The marketplace generates the 4 V's by design.

V₁
Volume
Every transaction across the customer–seller graph, growing weekly. Today: 96k orders · 3k sellers · 96k customers · 100k+ reviews. Tomorrow: ten times that.
V₂
Velocity
New orders, reviews, and delivery events arrive continuously. Risk scoring must refresh weekly — same code, same pipeline, every Monday.
V₃
Variety
Structured orders + Portuguese free-text reviews + geographic coordinates + network/graph relationships. Four data shapes, one pipeline.
V₄
Veracity
8.1% of orders are late. Worst state (AL) 23.9% vs best (SC) 9.8%. Missing reviews, inconsistent seller data — the analysis must absorb the noise.

Why Spark

Spark speaks the language of networks.

Each demand of this problem maps to a native Spark primitive — so the prototype is also the production path.

The network demands…
Spark delivers…
Joins across 9 interlinked tables, daily
Distributed joins + broadcast() on small lookups (sellers, products, geo centroids)
Graph analysis — who depends on whom?
GraphFrames — native PageRank, connected components, motifs, BFS
Weekly trends per seller + per category
Window functions + MLlib Pipelines for rolling features & cross-validation
Refresh as new orders arrive
Lazy execution + step cache — only what changed re-runs
Growth from thousands to millions of sellers
Same code, laptop today → cluster tomorrow (Databricks / EMR, zero rewrite)

Insights only the network reveals

Two findings you can't see from per-seller dashboards.

Delivery behaviour predicts.
Sentiment only confirms.
Reviews classify cleanly (LSTM AUC 0.96), but lead-correlation against weekly volume peaks at only |0.015| at 7 weeks. Delays move first — reviews catch up.

Hub sellers shift under stress.
